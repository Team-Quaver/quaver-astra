## 播放器换成 mpv（自研解码链全部下线）

**动机**：用户要求弃用 go-mp3 等自研解码器，统一交给 MPV。

**做法**：`internal/audio/audio.go`（793 行 oto+go-mp3+mewkiz-flac+oggvorbis）
整包删除，替换为 `internal/audio/mpv.go`——mpv 子进程 + JSON IPC。
选子进程而非 libmpv 的原因：本项目要交叉编译到
linux/{amd64,arm64,loong64}、windows/{amd64,arm64}、darwin/arm64，cgo 会破坏交叉编译。
本机有 `libmpv.so.2` 但无 dev 头文件（pkg-config 查不到），也是选 IPC 的原因。

go.mod 少了四个依赖：oto/v3、go-mp3、jfreymuth/oggvorbis、mewkiz/flac。

### 换引擎带来的实际收益（不只是"换个播放器"）

1. **全档位可播**：原先 `pickTier` 硬编码支持集
   `{128,320,320ogg,640ogg,flac}`，atmos/母带需嗅探降档；现在交给 FFmpeg，
   支持集改成「取未锁定档位里 rank 最高的一档」。
2. **位置不再靠墙钟推算**：旧 `tick()` 每 200ms 加 0.2s、seek/换歌要重锚定，
   误差会累积。现在直接读 mpv 的 `time-pos`，seek 落点立即准确。
   `Ended()` 改用 mpv 的 `eof-reached`，不再靠 `dur+0.3s` 猜。
3. `Backend` 接口删掉 `StreamOpen`——mpv 自己发 HTTP Range 与重试。

### mpv JSON IPC 踩的坑（都写进代码注释了）

1. **顶层必须是 JSON 对象 `{"command":[...]}`，不是数组**。
   发成数组 mpv 会当成 input.conf 文本命令
   （日志：`[input] Command '["command",' not found.`），永远没有响应。
2. **`--idle` 必须是无值形式**。写 `--idle=yes` 时 mpv 当成布尔开关、
   读完就退（`Exiting... (Quit)`），socket 刚建好进程就没了。
3. **握手期间绝不能启动 observe 协程**。socket 只有一个读消费位：
   observe 起来就抢上读锁并阻塞在读上（等事件，可能很久），
   握手的 `command()` 再也拿不到锁 → 双方互等，**启动即死锁**。
   正确做法：握手命令各自读回响应，握手完成后再 `go e.observe()`。
   （我第一版就是踩了这个，race 测试才暴露出来。）
4. **`loadfile` 必须异步下发（`async:true`）**。mpv 命令同步执行，
   执行期间不服务 socket；网络流加载几秒，同步等必然顶到读超时。
   代价是拿不到同步错误，改由 `end-file` 且 `reason=="error"` 回填
   `loadErr`，player 侧 `awaitLoaded()` 轮询等待，超时/报错即降下一档。
5. 读超时是必要的兜底：`loadfile` 在起播主流程上，mpv 卡死不能把调用方一起拖死。

## 复用 Quaver Music 本体的 MPV 处理（第二轮）

用户要求对齐本体（`/home/ne0w0r1d/Desktop/quaver`，`ui/electron/audio/dist/`）。

### 新增 internal/audio/bins.go：三级定位

本体 `bins.js` 的策略，本项目照搬：

    显式路径(QAA_MPV) → 随包目录(QAA_MPV_DIR) → PATH

随包候选：`mpv/AppRun`（AppImage 解包形态）、`mpv/mpv`、`mpv.exe`、`mpv`。

**`childEnv()` 是关键**：随包 mpv 是「目录形态」（自带 lib），
要把它相邻的 `lib/`、`usr/lib/` **追加到 LD_LIBRARY_PATH 末尾**。
放前面会导致「能解码但没声音」——音频输出库必须用宿主机的 pipewire/pulse。
本体注释里专门写了这一点。

bundled 分支只认「可执行文件」：AppImage 挂载点只读，运行时 chmod 必然失败，
宁可判定为「没有」落回 PATH，也不要 spawn 一个注定 EACCES 的路径。

### 从本体抄来的 mpv 参数改进

- `--stream-lavf-o=reconnect=1,reconnect_streamed=1,reconnect_delay_max=5`
  上游 CDN 半路断流由 lavf 自己重连
- `--cache-on-disk=no`（不落盘是合规硬线）
- `--volume-max=100`、`--force-window=no`、`--ytdl=no`、`--no-resume-playback`
- seek 用 `absolute+exact`（默认 absolute 会落到关键帧上，听感跳早几百毫秒）
- **起点走 `loadfile` 的 `options.start`**，不要载入后再 seek：
  mpv 会忽略文件就绪前的 seek，而那还得在带缓冲的网络流上多打一次 Range
- 观察 `paused-for-cache`：缓冲欠载是 mpv 方案的核心价值，UI 应能显示「缓冲中」
- `--really-quiet`、`--audio-display=no`

## 侧栏头像/图标对齐（用户截图反馈）

用户给了两张截图：头像没对齐图标、收起态要对齐靠中间。

**根因两处**：
1. `ui.Avatar` 默认尺寸 = `FontSize * 2.25`（≈32px），比导航图标（18px）大一大圈
2. 用户区行高 48 而导航项行高 40，垂直中心线对不上

**修法**：抽出统一常量（`sideBtnHeight=40`、`sideIconSize=18`、`sideAvatarSize=26`），
用户区行高改成与导航项一致，头像显式指定边长。
收起态的 Row 必须 `Center()`——只设 `AlignItems(Center)` 只管了交叉轴，
主轴仍靠左，这是「看着没对齐」的另一半原因。

### 顺手修的真实缺陷

`windowButtons()` 没有 `a.Win == nil` 保护，
而 `a.Win.IsMaximized()` 会把调用转发到主线程——无窗口环境（如无头测试）会**永久阻塞**。

## 用 MyGO Tester 做布局测试（重要方法论）

上一轮遗留「无法目视验证 UI 改动」——这台机器无显示服务，截图钩子跑不出图。
本轮发现 `ui.NewTester(view, w, h)` 可无头渲染 + 截图 + 点击，
`ui.Render` 也能出图。以后 UI 布局问题应当优先写断言，而不是靠肉眼看。

新增 `internal/appui/sidebar_test.go`：
- `TestSidebarIconColumnAligned` 用户区与导航项左边界重合
- `TestSidebarNavRowsEvenlySpaced` 各导航项行距均匀
- `TestSidebarCollapsedFooterIsVertical` 收起态底部两图标 x 相同、y 分开
- `TestSidebarGeometryInvariants` 几何常量自洽性

### 写这类测试踩的坑（重要）

1. **测试 App 不能走 `New()`**——会真连后端、真启 mpv。要手工搭最小状态：
   `Conf` 必须是真 `conf.Open(t.TempDir())`（nil 会 panic）、
   `Router` 停在 `/settings`（首页会 `ensureHome` 去连后端）、
   `Covers` 不能 nil、`player.New` 的 Engine 参数传空实现。
2. **tooltip 不进渲染树**（悬停才显示），无法用 `Find` 定位纯图标按钮。
3. **靠点击验证布局不可行**——第一次点击就改变了状态，第二次点击时布局已变。
4. **按钮是透明底，只有图标有颜色**。按「与底色不同」扫描像素时，
   命中的是图标笔画而非按钮边界——第一版就是这么写出假阳性的
   （扫到两段图标线就报告「两个按钮」）。必须明确扫的是图标。
5. **扫描窗口要避开其他图标**：歌单区的音符图标也在侧栏中线 x 上，
   起点落在它们下方才不会混进来。
6. `hasIconAt(img, x, yFrom, yTo, isIcon)` 里yTo 要传 `y`（单行），
   传 `y1` 会扫描整个剩余范围导致恒为真、聚类全并成一簇。

实测真实坐标（1000×700 窗口、收起态）：设置图标 (32,551)、展开图标 (31,589)——
x 相同、y 相差 38px，纵向排列正确。
